# CLI / Setup UX 重设计方案

## 1. 背景与问题

当前 `ctr setup` 的用户入口与项目已经明确的产品心智不一致：

- 项目主心智已经转向 `Models[].id` + `Router.default`
- 模板层已经能直接产出 model-id-first 配置
- 旧 `claude-code-router` 配置也已经具备可探测、可迁移基础
- 但当前 CLI 主入口仍然以 provider preset 为第一步，要求用户先理解接入实现，而不是先解决“如何最快得到一个可用 Router”

这种错位会导致三个直接问题：

1. 迁移路径没有成为优先入口，老用户被迫重新理解新流程
2. 新建路径仍然是 provider-centric，而不是 model-id-centric
3. CLI、README、配置模板三者对外叙事不一致，增加理解和使用成本

本设计的目标不是只在现有流程前面补一个“是否迁移”的问题，而是整体重排 CLI 入口心智，让 `setup` 从“配置 provider”转向“生成可用配置”。

---

## 2. 设计目标

### 2.1 核心目标

- `ctr setup` 必须首先帮助用户复用已有成果，而不是默认从零开始
- `ctr setup` 必须围绕用户目标组织交互，而不是围绕内部 provider/preset 组织交互
- 新建配置路径必须以 `Models[].id` 为中心
- provider preset 必须退化为新建接入时的辅助输入器，而不是主入口
- CLI、README、模板输出、后续 UI 叙事必须统一为同一套产品心智

### 2.2 非目标

本次设计不包含以下内容：

- 不重新设计运行时路由算法
- 不修改统一 Router 演进方案的结构边界
- 不在 setup 第一阶段暴露完整高级路由能力
- 不把 setup 做成覆盖全部高级配置的万能入口

---

## 3. 产品心智

### 3.1 `setup` 的角色

`ctr setup` 的职责应被重新定义为：

> 检测当前环境，优先复用或迁移已有配置；若不可复用，再帮助用户创建一份最小可用的 model-id-first 配置，并在完成后说明结果与下一步。

这意味着：

- `setup` 首先是“环境接入向导”，不是“provider 配置器”
- `setup` 的第一优先级是减少重复录入
- `setup` 的完成标准是“可运行”，不是“高级功能齐全”

### 3.2 用户可见心智

CLI 对用户暴露的主概念应收敛为：

- 当前配置能不能直接用
- 是否需要迁移旧 `claude-code-router` 配置
- 当前要创建哪些模型 id
- 哪个模型 id 作为默认路由
- 是否现在就需要开启高级路由能力

以下概念不应出现在 setup 首页：

- provider preset 列表
- 旧字段兼容细节
- 内部 schema 转换术语
- 复杂 governance 拓扑

---

## 4. 命令分工重定义

### 4.1 `ctr setup`

定位：面向大多数用户的主入口。

负责：

- 探测当前状态
- 优先复用已有配置
- 优先迁移旧配置
- 必要时新建最小可用配置
- 在成功后可选启动服务并进入 `ctr code`

不负责：

- 暴露所有高级配置细节
- 教用户理解全部路由模块
- 要求用户先理解 provider/preset 概念

### 4.2 `ctr init`

定位：写入最小模板文件的低干预入口。

负责：

- 生成最小模板
- 指明用户应补全 `Models` 和 `Router.default`

不负责：

- 承担 setup 的交互式引导职责
- 使用旧的 `Providers` 叙事

### 4.3 `ctr help`

定位：统一产品叙事的外层入口。

帮助文案必须体现：

- `setup` 是推荐主入口
- 推荐路径是“复用/迁移优先，其次新建最小配置”
- 用户先理解 `Models` 与默认模型即可开始使用

---

## 5. 顶层决策架构

`ctr setup` 的顶层流程固定为三段：

1. 状态探测
2. 入口决策
3. 结果落盘与下一步指引

### 5.1 状态探测

setup 启动后必须统一探测：

- 当前 `claude-trigger-router` 配置是否存在
- 当前配置是否基本可用
- 是否检测到旧 `claude-code-router` / `ccr` 配置
- 当前服务是否已运行

探测结果必须先内部归一成明确状态，再进入交互，不允许一边探测一边零散提问。

推荐状态枚举：

- `current_usable`
- `current_incomplete`
- `legacy_available`
- `fresh_start`

### 5.2 入口决策顺序

顶层分支顺序必须固定：

1. 当前配置可复用时，先问是否直接沿用或调整
2. 当前不可直接复用但存在旧配置时，先问是否迁移旧配置
3. 只有当前两者都不成立，或用户主动跳过时，才进入新建流程

这条顺序是本次设计的硬约束，后续实现不得回退成 preset-first。

---

## 6. 详细交互设计

## 6.1 场景 A：当前配置已可用

目标：避免用户重复配置。

首屏主问题：

- `检测到当前 claude-trigger-router 配置已可用。你想直接使用它，还是重新调整？`

选项：

- `直接使用当前配置（推荐）`
- `检查并调整当前配置`
- `放弃当前配置，重新开始`

行为要求：

- 选择“直接使用当前配置”时，应展示当前默认模型、已配置模型 id 数量、服务状态摘要
- 若用户选择继续，可直接进入“启动服务 / 进入 Claude Code”步骤
- 不应在此场景下默认把用户重新带入 provider/preset 选择

## 6.2 场景 B：发现旧 `ccr` 配置

目标：让迁移成为默认路径。

首屏主问题：

- `检测到旧 claude-code-router 配置。是否迁移为当前推荐配置？`

选项：

- `迁移旧配置（推荐）`
- `先预览迁移结果`
- `跳过迁移，手动新建`

行为要求：

- `迁移旧配置` 应直接导向标准化后的 `Models + Router.default` 结果
- `预览迁移结果` 应展示迁移后将生成的模型 id、默认路由、保留的关键字段
- `跳过迁移` 才允许进入 fresh path

这里的重点不是“告知支持迁移”，而是让“迁移”成为用户默认且最低成本的行为。

## 6.3 场景 C：从零新建

目标：让新用户先获得一份可用配置，而不是先学习 provider taxonomy。

首屏主问题：

- `我们先创建一份最小可用配置。你要先接入哪个默认模型？`

此后顺序必须是：

1. 确定默认模型 id
2. 选择接入方式
3. 填写 endpoint / key / upstream model
4. 生成最小配置
5. 可选继续添加第二个模型
6. 可选进入高级路由配置

### 6.3.1 默认模型 id 优先

第一问必须是用户要使用的默认模型逻辑名，例如：

- `sonnet`
- `main`
- `coding`

而不是：

- `openrouter`
- `anthropic`
- `custom`

原因是用户首先需要定义“我在本地如何引用它”，而不是“它来自哪家 provider”。

### 6.3.2 provider preset 的降级定位

在新建流程中，provider preset 只能以如下形式出现：

- `这个模型接到哪里？`
- 选项：`使用常见接入模板` / `手动填写接口`

若用户选择 `使用常见接入模板`，才出现 preset 选项，例如：

- `OpenRouter`
- `Anthropic`
- `DeepSeek`
- `OpenAI-compatible`
- `Custom`

这时 preset 的职责只是：

- 预填 `api`
- 预设 `interface`
- 提供示例 `model`
- 提供提示文案

它不再承担 setup 顶层入口的产品含义。

### 6.3.3 最小配置优先

新建流程第一阶段只应生成：

- 至少一个 `Models[]`
- `Router.default`

如无明确需要，不应在主流程强行暴露：

- `TriggerRouter.rules`
- `SmartRouter.candidates`
- `Governance` 细项

完成最小配置后，可追加询问：

- `现在要不要继续添加一个“复杂任务专用模型”？`
- `现在要不要开启高级路由？`

这些都必须是第二阶段增强，而不是初始门槛。

---

## 7. 交互文案规范

### 7.1 文案原则

所有 setup 问题都应满足：

- 从用户目标出发
- 避免内部术语优先
- 优先使用动作型表达
- 用户无需理解底层 schema 也能完成流程

### 7.2 推荐文案风格

推荐：

- `检测到旧配置，是否迁移？`
- `我们先创建一份最小可用配置`
- `这个模型在本地要叫什么名字？`
- `它连接到哪个接口？`
- `是否把它设为默认模型？`

不推荐：

- `选择 provider 预设`
- `请输入 provider name`
- `选择协议类型`
- `配置 TriggerRouter / SmartRouter`

除非用户主动进入高级模式，否则不应把内部结构直接抛给用户。

---

## 8. 配置输出要求

setup 的输出摘要必须围绕“生成结果”组织，而不是围绕“输入来源”组织。

完成后应展示：

- 默认模型 id
- 已创建模型 id 列表
- 每个模型接入的接口类型
- 是否启用高级路由
- 下一步建议命令

示例：

```text
已生成配置：
- 默认模型：sonnet
- 已创建模型：sonnet
- 接口类型：openai-compatible

下一步：
1. ctr start
2. ctr code
```

不应再输出类似：

- `你选择了某个 provider preset`
- `请去 Providers 下继续补配置`

---

## 9. CLI / README / 模板一致性要求

以下入口必须统一对外叙事：

- `src/cli.ts` help 文案
- `ctr init` 成功后的 next steps
- `README.md` 快速开始
- setup 完成后的摘要输出

统一规则：

1. 始终先讲 `Models`
2. 始终强调 `Router.default`
3. 始终把高级路由表达为增强层
4. 不再把 `Providers` 作为主叙事中心

如果 CLI 帮助、README、setup 完成页三者中任意一处仍使用旧 provider-centric 叙事，则视为本次设计未完成。

---

## 10. 分阶段实施预期

### Phase 1：入口重排

目标：把 `setup` 首屏决策顺序改成“复用/迁移优先”。

预期结果：

- 可用当前配置优先复用
- 发现旧配置时优先提供迁移
- fresh path 不再直接从 preset 开始

### Phase 2：fresh path 重构

目标：把新建流程改成 model-id-first。

预期结果：

- 默认模型 id 先于 provider 选择
- provider preset 仅作为接入模板
- 最小配置默认只生成 `Models + Router.default`

### Phase 3：文案与产物统一

目标：统一 CLI、README、init、setup 输出。

预期结果：

- 帮助文案不再使用旧 `Providers` 心智
- next steps 与实际配置结构一致
- setup 摘要输出能明确表达生成结果

### Phase 4：高级能力延后暴露

目标：将高级路由能力改为可选增强。

预期结果：

- 初次 setup 不再强迫用户理解高级路由结构
- 高级能力在基础配置完成后再引导开启

---

## 11. 验收标准

### 11.1 用户路径验收

- 有可用当前配置的用户，可以在不重新录入 provider 信息的情况下完成 setup
- 有旧 `ccr` 配置的用户，进入 setup 后第一优先动作是迁移，而不是新建 provider
- 新用户可以在不了解 provider taxonomy 的情况下生成一份可用配置
- 单模型用户可以在最短路径内完成 setup，而不被高级路由问题打断

### 11.2 交互逻辑验收

- 任意 fresh path 中，第一问都不是 provider preset
- provider preset 只出现在“选择接入方式”的子步骤中
- setup 首页不出现 `Providers` 作为主概念
- setup 结束页展示的是模型 id 与默认路由结果，而不是 provider 选择过程

### 11.3 一致性验收

- `README.md` 快速开始与 setup 行为一致
- `ctr init` 提示与当前配置结构一致
- `ctr help` 对 `setup` 的解释与新流程一致

---

## 12. 进展跟踪表

| 阶段 | 目标 | 关键结果 | 验收信号 |
|---|---|---|---|
| Phase 1 | 入口重排 | 复用/迁移优先 | setup 首屏不再跳 preset |
| Phase 2 | fresh path 重构 | model-id-first | 默认模型 id 成为 fresh path 第一问 |
| Phase 3 | 文案统一 | CLI/README/init 一致 | 不再出现旧 `Providers` 主叙事 |
| Phase 4 | 高级能力后置 | 先可用后增强 | 单模型用户不再被高级路由打断 |

---

## 13. 实施要求

- 必须复用已有探测与迁移能力，不允许重写一套平行逻辑
- 必须在现有 setup 决策树上做结构重排，而不是只补提示文案
- 必须以 `Models[].id` 作为所有新交互的中心对象
- 必须保证最小可用配置路径最短
- 必须同步修改 CLI 帮助、init 提示、README 快速开始，否则不算完成

---

## 14. 防偏离约束

以下情况一旦出现，视为实施偏离本设计：

- 只是把“是否迁移”插到现有 preset-first 流程前面，但 fresh path 仍然是 provider-first
- setup 仍要求用户先理解 `Providers` 再理解 `Models`
- 高级路由配置再次回流为初始 setup 必答项
- `README` 与 CLI 文案没有同步改写
- setup 输出仍按 provider 组织，而不是按 model id 与默认路由组织

本设计的核心不是“迁移入口前置”这一条局部修补，而是把 CLI/setup 的产品入口从“内部接入视角”重构为“用户任务视角”。
