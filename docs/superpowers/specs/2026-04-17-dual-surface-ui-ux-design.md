# UI 双层工作台设计

> **统一进展承接说明（2026-04-16）**
>
> 本文档承接 `docs/superpowers/plans/unified-progress-baseline.md` 中“UI 双层工作台收敛”这一行的设计输入。
>
> 当前职责：承接使用者界面 / 维护者界面的产品分层、信息架构与演进顺序；统一进展入口只维护状态与闭环结论。

## 1. 背景

当前 `/ui` 已经同时承载多类能力：

- 配置草稿编辑
- compiled preview 与 warning 修正
- governance metrics / anomaly / archive / snapshot 观测
- 服务状态与维护信息

这说明 `/ui` 已经具备产品雏形，但也暴露了当前问题：

- 使用者要做日常配置时，会看到过多维护侧信息
- 维护者查看治理观测时，又会与配置编辑路径混在一起
- 当前界面是“能力堆叠”，还不是“角色分层”的信息架构

因此需要把 UI 明确拆成两类工作台。

## 2. 设计定位

UI 双层工作台不作为新的独立总体系，而是并入现有 UI/UX 主线推进，原因是：

- 它本质上是现有 `/ui` 能力的产品分层，而不是新增运行时能力
- 它与 `ctr setup`、README、配置产品化和治理观测都有强耦合
- 如果脱离现有 UX 主线单独推进，容易形成新的叙事割裂

统一定位：

> `/ui` 需要从“能力集合页”演进为“使用者界面 + 维护者界面”双层工作台，其中前者面向配置与使用，后者面向观测与维护。

## 3. 设计目标

### 3.1 核心目标

- 明确使用者与维护者的主任务边界
- 降低配置编辑路径的认知负担
- 让治理观测、告警、归档和服务状态拥有稳定入口
- 让 CLI/setup/README 与 `/ui` 的产品心智一致

### 3.2 非目标

本轮不追求：

- 直接做完整 RBAC 权限体系
- 把所有高级维护能力一次性可视化完
- 用 UI 替代全部 CLI 能力
- 在首轮把所有页面都重写一遍

## 4. 双层工作台定义

### 4.1 使用者界面

主要目标：快速得到可用配置并完成日常修改。

应重点覆盖：

- 模型配置新增、修改、删除
- 默认模型与路由基础项设置
- capability / warning 的易用修正
- 高阶能力的简化配置入口
- compiled preview 与保存结果确认

使用者界面关注的问题是：

- 我怎么把 Router 配起来
- 我现在有哪些模型
- 保存后是否可用
- 常见 warning 怎么快速修正

### 4.2 维护者界面

主要目标：查看运行状态、治理信号与维护信息。

应重点覆盖：

- governance metrics
- anomaly alerts
- trace / exports / snapshots / archives
- 服务状态、健康信息与后续远程注册摘要
- 长时间窗口下的观测与维护操作

维护者界面关注的问题是：

- 当前服务稳不稳定
- 有没有告警或异常趋势
- 历史归档与快照怎么查看
- 当前运行服务和配置是否一致

## 5. 现有 `/ui` 能力归类

### 更适合归入使用者界面

- Draft Config Editor
- Models 表单
- capability 显式字段编辑
- Validation Summary
- Capability Warnings 快捷修正
- compiled model preview
- 保存当前草稿配置

### 更适合归入维护者界面

- governance metrics 概览
- anomaly alerts
- route / model / intent 排行
- buckets 趋势表
- exports / snapshots / schedules / archives
- 服务运行状态与观测摘要

## 6. 信息架构建议

建议把 `/ui` 顶层导航改成：

```text
/ui
  -> 使用者工作台
     -> 配置总览
     -> 模型管理
     -> 默认路由与高阶能力
     -> 预览与保存
  -> 维护者工作台
     -> 运行概览
     -> 治理观测
     -> 告警与异常
     -> 快照 / 导出 / 归档
     -> 服务与远程接入状态
```

### 顶层导航原则

- 先按角色任务分区，而不是按底层模块分区
- 页面名称使用任务型命名，而不是内部实现名词
- 使用者入口优先暴露“配置可用性”
- 维护者入口优先暴露“当前运行状态”

## 7. 与 CLI / setup / README 的关系

### 7.1 与 `ctr setup`

- `ctr setup` 是首次进入的引导入口
- setup 成功后应优先导向使用者界面，而不是直接落到维护侧信息页

### 7.2 与 README

- README 中的 `/ui` 说明需要区分“配置入口”与“维护入口”
- 不应继续把 `/ui` 笼统描述成一个混合调试页

### 7.3 与配置产品化

- 使用者界面应复用配置产品化已建立的 schema、preview、warning、repair 路径
- 不应额外复制一套只属于 UI 的配置心智

### 7.4 与治理观测

- 维护者界面应直接承接 metrics、alerts、archives、snapshots 等现有能力
- 不再把这些能力混在默认配置编辑首页里

## 8. 远程接入对 UI 的影响

当部署形态进入 server/cloud 阶段后，双层工作台还需要显式表达：

- 当前正在管理的是本地服务还是远程服务
- 当前配置保存作用于本地还是远端
- 当前维护数据来自哪个服务实例

这意味着未来 UI 顶部需要具备清晰的 service context 切换区。

## 9. 风险

| 风险 | 影响 | 缓解策略 |
|---|---|---|
| 使用者与维护者路径继续混杂 | 界面越来越重 | 先做导航分层和首页拆分 |
| 信息重复 | 同一能力多处维护 | 共用底层数据接口，只分角色呈现 |
| 维护者能力暴露过早 | 新用户被复杂度劝退 | 默认先进入使用者工作台 |
| CLI/UI 心智再次分裂 | 用户路径不一致 | setup/README/UI 同步改写 |

## 10. 验收标准

### 信息架构验收

- 能清楚区分使用者工作台与维护者工作台的首页职责
- 当前主要页面可以明确归类，不再全部堆在一个入口里

### 使用者路径验收

- 用户能在最短路径内完成配置、预览、修正 warning 和保存
- 使用者首页不再被治理观测细节打断

### 维护者路径验收

- 维护者能稳定查看 metrics、alerts、archives、service status
- 维护侧信息具备相对独立的导航和上下文

## 11. 推进顺序

建议按以下顺序推进：

1. 先完成现有页面能力归类
2. 再做顶层导航与首页分层
3. 然后整理使用者工作台的配置主路径
4. 最后收拢维护者工作台的观测与运维能力

## 12. 结论

UI 双层工作台的核心，不是把页面机械分两组，而是让 `/ui` 真正从“功能堆叠”演进为“按角色任务组织的产品界面”，让配置与维护都各回其位。
