# 首次使用一键向导（`ctr setup`）设计文档

> **统一进展承接说明（2026-04-16）**
>
> 本文档承接 `docs/superpowers/plans/unified-progress-baseline.md` 中“`ctr setup` 早期实施计划”这一行所关联的 setup 易用性设计输入。
>
> 当前职责：保留首次使用入口设计依据；后续 setup / UX 重设计的详细方案以下游专项文档为准。


**目标**

为 Claude Trigger Router 增加一个面向新手的首次使用入口 `ctr setup`，把“检查配置、迁移旧 ccr 配置、生成最小可用配置、启动服务、进入 `ctr code`”收敛成一条可走通的向导路径。

## 背景

当前项目已经在配置结构、服务探活、配置保存校验和文档主线上完成了收口，但首次使用仍然偏工程化：

- 用户需要理解 `ctr init`、`ctr start`、`ctr code` 的关系
- 用户需要手动编辑 YAML 才能得到最小可用配置
- 已有旧 `ccr` 配置的用户缺少迁移入口
- 文档已经比之前清楚，但首次跑通仍依赖用户自己拼接步骤

这会让新手第一次使用时承担过多心智负担。产品层面的优化方向不是再加一份更长的文档，而是给出一条明确的“第一次就跑通”的命令入口。

## 设计结论

采用方案 A：新增 `ctr setup`。

它是首次使用专用向导，不替代现有 `ctr init` / `ctr start` / `ctr code`。老用户仍可以按原有方式使用；新用户只需要记住一个命令。

## 用户体验目标

用户执行：

```bash
ctr setup
```

理想成功路径：

1. 检查当前是否已有 Claude Trigger Router 配置
2. 检查是否存在旧 `ccr` 配置
3. 如果发现 `ccr` 配置，询问是否迁移
4. 如果没有可迁移配置，则进入全新初始化
5. 询问 provider、`api_base_url`、`api_key`、默认模型
6. 生成并校验一份最小可用配置
7. 启动服务
8. 用健康检查确认目标端口上确实是本服务
9. 自动进入 `ctr code`

向导的最终成功标准不是“配置文件写好了”，而是“用户真的进入了 `ctr code`”。

## 范围

### 本次会做

- 新增 `ctr setup` 命令
- 检测现有 Claude Trigger Router 配置
- 检测旧 `ccr` 配置并提供迁移入口
- 基于交互生成最小单模型可用配置
- 复用现有配置校验逻辑，在写入前验证
- 复用现有服务启动与健康检查逻辑
- 成功后自动进入 `ctr code`
- 更新 README 快速开始与配置指南

### 本次不会做

- 不在 setup 中配置完整 TriggerRouter / SmartRouter 高级规则
- 不做完整可视化 Web UI
- 不自动探测用户有哪些模型权限
- 不尝试迁移所有 `ccr` 的高级字段
- 不替代现有 `init/start/code` 命令

## 交互设计

### 1. 入口定位

`ctr setup` 是“第一次跑通”的专用入口。

- 新手：优先使用 `ctr setup`
- 老用户：继续使用 `ctr init` / `ctr start` / `ctr code`
- 文档：把 `ctr setup` 放到快速开始主路径，原命令作为手动路径保留

### 2. 交互原则

- 每一步只收集当前必须的信息
- 只在需要时提问，不把所有选项一次性抛给用户
- 术语尽量少，默认用户不理解 TriggerRouter / SmartRouter / transformer 等内部概念
- 以“下一步该做什么”为中心，而不是以“系统内部发生了什么”为中心

### 3. 分支优先级

为了避免 setup 在“已有当前配置”和“旧 `ccr` 配置”同时存在时走出歧义分支，优先级规则固定如下：

1. 先检查当前 Claude Trigger Router 配置
2. 如果当前配置存在且校验通过，默认优先复用，不再主动提示迁移旧 `ccr`
3. 只有当当前配置不存在，或用户明确选择“备份后覆盖 / 重建”时，才进入旧 `ccr` 检测与迁移分支
4. 如果当前配置存在但不合法，优先进入“修复模式”，而不是直接要求用户从头填写

### 4. 推荐交互顺序

1. 检测是否已有当前项目配置
2. 如果当前配置存在，先执行校验
3. 若当前配置合法，询问是“直接复用并继续”、“备份后覆盖”还是“退出 setup”
4. 若当前配置不合法，进入修复模式，只补缺失或非法字段
5. 仅在当前配置不存在，或用户明确选择覆盖时，检测是否存在旧 `ccr` 配置
6. 若发现旧配置，询问是否迁移
7. 若不迁移或迁移失败，开始全新初始化
8. 选择 provider 类型
9. 输入 `api_base_url`
10. 输入 `api_key`
11. 选择或输入默认模型
12. 展示将要写入或修复的最小配置摘要
13. 写入配置并校验
14. 启动服务并探活
15. 进入 `ctr code`

### 5. provider 预设

为了减少输入量，setup 提供少量常见预设：

- `openrouter`
- `deepseek`
- `openai-compatible`
- `custom`

预设的作用是提供默认 provider 名称与常见 API 入口格式，不是限制用户只能使用这些上游。

## 迁移设计

### 1. 迁移目标

迁移只追求“最小可用迁移”，不是“全量语义保真迁移”。

首次向导的任务是跑通，不是把旧系统的所有复杂配置一次性无损搬过来。

### 2. 优先迁移的信息

- provider 名称
- `api_base_url`
- `api_key`
- `models`
- 默认模型映射

### 3. 不稳定字段处理策略

如果旧 `ccr` 配置中的字段在当前项目里没有明确、稳定、可验证的语义，则 setup 不自动迁移，只会：

- 明确提示该字段被跳过
- 保留“之后手动补高级配置”的路径

### 4. 补全模式

如果迁移结果不能组成一份合法最小配置，setup 不会要求用户从头重填，而是进入补全模式，只追问缺失字段。

## 配置生成策略

### 1. 默认只生成最小单模型配置

首次向导默认输出：

- 一个 provider
- 一个默认模型
- 可直接用于 `ctr code` 的最小配置

也就是说，首次向导不会默认帮用户生成复杂 TriggerRouter / SmartRouter 配置。

### 2. 原因

这是有意收窄：

- 首次跑通路径越短，成功率越高
- 高级分流适合在用户确认基本链路可用之后再配置
- 当前项目已经有 `docs/configuration-guide.md` 承担“从能用到好用”的进阶教学

### 3. setup 结束后的引导

向导成功结束后可以追加一条简短提示：

- 现在已经可以使用
- 如果想继续做多模型分工，请查看 `docs/configuration-guide.md`

## 错误与回退设计

### 1. 已有配置

如果发现已有 Claude Trigger Router 配置，setup 先校验该配置，再分两类处理：

- 配置合法：提供“直接复用并继续后续步骤”“备份后覆盖”“退出 setup”三个选择
- 配置不合法：提示“检测到现有配置但不可直接使用”，提供“补全修复”“备份后覆盖”“退出 setup”三个选择

### 2. 现有配置不可解析

如果当前配置文件本身无法解析，例如 YAML 语法错误、JSON 结构损坏或文件内容已不可读：

- setup 先展示解析错误
- 不承诺进入“只补字段”的修复模式
- 提供“备份后重建”“改用手动编辑后重试”“退出 setup”三个选择

### 3. 现有配置修复模式

当当前配置可以解析、但校验不通过且用户选择修复时：

- setup 先展示当前配置缺失或非法的字段错误
- 只追问缺失字段和校验失败字段，不要求用户从头重填
- 修复后的配置仍需重新经过 `normalizeAndValidateConfig(...)`
- 只有用户明确选择覆盖时，才重新生成一份最小单模型配置

### 4. `ccr` 配置读取失败

如果检测到旧配置但读取失败：

- 显示简短错误
- 提供“跳过迁移，继续全新初始化”路径
- 不阻塞整个 setup

### 3. 配置校验失败

如果生成后的配置未通过现有校验逻辑：

- 展示具体字段错误
- 返回到对应字段重新输入
- 不进入服务启动阶段

### 5. 服务已在运行

如果目标端口上已经是 Claude Trigger Router，且健康检查通过：

- 只有在本次 setup 没有修改配置时，才允许直接复用现有服务继续后续步骤
- 只要本次 setup 完成了迁移、修复或覆盖写入，就不能静默复用旧进程
- 对于已经改写配置的场景，setup 必须重启服务或触发现有重载路径，再重新做健康检查
- 仍然在进入 `ctr code` 之前再次做一次最终健康检查

### 6. 服务启动失败

如果服务启动失败：

- 停在 setup 中
- 提示用户可以改用 `ctr start` 查看详细错误
- 不误报“已完成”

### 6. 端口冲突或健康检查失败

如果端口不可达，或端口上不是本服务：

- 明确提示 setup 未完成
- 如果是非本服务占用目标端口，提示用户修改端口或改用手动命令处理
- 不自动覆盖端口占用，也不自动杀进程
- 不进入 `ctr code`

### 7. Claude Code 启动失败

如果 `claude` 命令本身启动失败：

- 保留已生成配置
- 保留已经成功启动的服务
- 不做自动回滚
- 给出下一步建议，例如手动安装 Claude Code CLI 或单独执行 `ctr code`

## 实现结构

### 1. CLI 保持轻量

`src/cli.ts` 只负责：

- 解析 `setup` 命令
- 调用 setup 模块入口

不要把整条交互向导直接堆进 `src/cli.ts`。

### 2. 推荐模块划分

#### `src/setup/setup.ts`

负责整个 setup 流程编排：

- 检测当前配置
- 检测旧 `ccr` 配置
- 决定迁移或全新初始化
- 采集输入
- 生成配置
- 调用校验与写入
- 启动服务
- 进入 `ctr code`

#### `src/setup/detect.ts`

负责环境检测：

- 当前 Claude Trigger Router 配置是否存在
- 旧 `ccr` 配置是否存在
- 其路径与可读性状态

#### `src/setup/migrate.ts`

负责把旧 `ccr` 配置转换成当前项目的最小配置草稿。

#### `src/setup/prompts.ts`

负责 setup 中的提问逻辑、默认值、枚举选项和用户输入规范化。

#### `src/setup/templates.ts`

负责生成最小配置对象，而不是直接拼接 YAML 文本。

### 3. 复用现有逻辑

#### 配置校验与写入

继续复用 `src/utils/config.ts` 中已有的：

- `normalizeAndValidateConfig(...)`
- `writeConfigFile(...)`
- 现有 provider/model 交叉校验机制

#### 服务探活

继续复用 `src/service-health.ts` 中的健康检查。

#### 启动与进入 Claude Code

尽量复用现有 CLI 中的启动服务与 `runClaudeCode()` 路径，而不是重新实现一套接入逻辑。

## 测试策略

### 1. 单元测试

- 检测当前配置是否存在
- 检测 `ccr` 配置是否存在
- 迁移逻辑的成功与失败
- 最小配置模板生成
- provider 预设与默认值逻辑

### 2. 流程测试

- 无配置场景下，setup 能生成配置、启动服务并进入 `ctr code`
- 有 `ccr` 配置时，setup 能走迁移路径
- 有合法当前配置时，setup 能直接复用并进入 `ctr code`
- 配置校验失败时，setup 会停在当前输入阶段
- 当前配置文件不可解析时，不会误入“只补字段”的修复模式
- 服务启动失败时，不会误报成功
- 健康检查失败时，不会进入 `ctr code`
- 本次 setup 改写过配置时，成功路径需要明确断言服务已按新配置重启或重载后再进入 `ctr code`
- 成功路径需要明确断言最终调用了进入 `ctr code` 的逻辑

### 3. 边界测试

- 现有配置存在且合法时的复用分支
- 现有配置存在但非法时的修复模式
- 现有配置文件不可解析时的回退分支
- 当前配置与旧 `ccr` 配置同时存在时的优先级行为
- 迁移结果字段不全时的补全模式
- 目标端口已有健康 Router 服务时的复用行为
- 本次 setup 改写配置后，目标端口已有健康 Router 服务时不会静默复用旧进程
- 目标端口被非本服务占用时的失败提示
- `claude` 命令不存在时的失败提示

## 备选方案与放弃原因

### 方案 B：把 `ctr code` 直接升级成自动向导入口

优点：用户只需要记住一个命令。

放弃原因：

- `ctr code` 语义会过重
- 运行命令与首次初始化流程耦合过深
- 失败分支会变复杂，后续维护成本更高

### 方案 C：把 `ctr init` 改成交互式初始化

优点：改动贴近现有命令集。

放弃原因：

- 仍然需要用户再执行 `ctr code`
- 无法形成真正的一键闭环
- 不符合这次“最终进入 `ctr code`”的目标

## 验收标准

满足以下条件即可认为本次设计实现成功：

1. 新用户在没有现有配置的情况下，执行 `ctr setup` 能生成合法最小配置
2. 如果检测到旧 `ccr` 配置，`ctr setup` 能迁移出可运行配置；缺失信息进入补全流程
3. setup 成功结束时，服务已通过健康检查，并成功以最新配置进入 `ctr code`
4. README 和配置指南都把 `ctr setup` 作为首选首次使用路径
5. CLI 帮助文本已经把 `ctr setup` 标为首次使用入口，并清楚保留 `ctr init` / `ctr start` / `ctr code` 的手动路径

## 总结

这次易用性优化的核心不是扩展更多功能，而是把“第一次跑通”这条路径明确做成一个产品入口。`ctr setup` 让新用户不必先理解完整命令体系，也不必先手写配置文件；而对已有用户来说，原有命令和高级配置能力不受影响。这样能在保持工程边界清晰的前提下，把首次成功率显著拉高。

## 2026-04-06 设计校准

基于当前实现状态，这份设计文档需要增加两个现实判断：

### 1. `ctr setup` 设计目标已基本落地

原设计聚焦的关键闭环——检测、迁移、最小配置生成、服务接线、进入 `ctr code`——已经不再只是设计目标，而是已交付能力的一部分。

因此，这份文档后续应更多承担“为什么这样设计”和“边界为何如此定义”的作用，而不是继续作为待实现 spec。

### 2. 易用性问题已经从 setup 扩展到统一配置抽象

当前产品问题已经不只是“如何让新手第一次跑通”，还包括：

- 如何让不同 provider 的模型配置尽量统一
- 如何让 provider 差异不直接泄漏到用户主配置心智中
- 如何让 `/ui` 成为配置草稿、影响分析、修复建议和 dry-run 的工作台

因此，setup 设计已经自然延伸到更大的配置产品化命题：

- `Models` 抽象
- provider template
- 路由引用分析与修复
- preset merge / dry-run / summary

### 3. 下一阶段设计关注点

下一阶段应从“让 setup 更完整”转向“让模型配置更统一、更少参数、更少协议差异暴露”，重点是验证如下方向：

- 是否能把单个模型配置收敛为 `api` / `key` / `接口类型` / `思考类型（可选）`
- 是否能由路由层统一做消息格式转换，而不是把 OpenAI / Anthropic 差异暴露给每个配置入口
- 是否能让 setup、配置文件和 `/ui` 三条路径共享同一套模型抽象与编译逻辑
