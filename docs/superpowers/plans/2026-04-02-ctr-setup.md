**Architecture:** 方案以 `src/setup/` 目录承接交互向导逻辑，`src/cli.ts` 只接命令入口。setup 流程按“检测当前配置 → 决定复用/修复/覆盖/迁移 → 收集缺失字段 → 写入并校验配置 → 启动或复用服务 → 进入 Claude Code”编排，并复用现有配置校验、服务健康检查与 `runClaudeCode()` 闭环。为避免 orchestrator 失控，把分支决策、字段修复映射、备份写入和服务应用策略拆到独立模块，`src/setup/setup.ts` 只保留流程编排。

**Tech Stack:** TypeScript, Node.js CLI, Vitest, js-yaml, 现有 `src/utils/config.ts` / `src/service-health.ts` / `src/cli.ts`

## Hard Rules

- 修复模式必须只追问校验失败或缺失的字段，禁止退化为全量重填。
- 只有在本次 setup 未改写配置时，才允许复用当前健康服务。
- 只要本次 setup 发生迁移、修复或覆盖写入，就必须经过 `src/setup/service.ts` 的 start / reload / restart 路径再进入 `ctr code`。
- 只有在 detect 成功、且需要写配置时 persist 成功、且 service 成功后，才允许进入 `ctr code`。
- 用户取消、detect 失败、persist 失败、service 失败、端口被非本服务占用时都不得进入 `ctr code`。
- `enterClaudeCode` 失败时，不回滚配置，不停止已就绪服务。
- 流程测试不得真实启动交互式 `claude`；必须用依赖注入断言调用控制流和参数。
- `src/setup/setup.ts` 只保留流程编排，不直接处理备份命名、字段修复映射或服务复用矩阵细节。

## Test Seams

实现时必须通过依赖注入或适配器隔离这些副作用边界：

- prompt I/O
- 文件系统读取与写入
- 配置备份
- 服务启动 / 重启 / 重载
- 健康检查与端口探测
- `runClaudeCode()` / 进入 `ctr code`

`src/setup/setup.test.ts` 除了 happy path，还必须包含反向断言：
- parse error 路径不得调用 `mapConfigErrorsToRepairFields`
- 合法当前配置复用路径不得调用 `persistConfig`
- 非本服务占用路径不得调用 `enterClaudeCode`
- 用户取消路径不得调用 `persistConfig` 或 `enterClaudeCode`

## Module Contracts

- `detectSetupEnvironment()`
  - 输入：依赖注入的 config reader、legacy reader、service probe
  - 输出：`{ currentConfig, legacyCcrConfig, detectedService }`
  - 只负责探测，不做分支判断

- `decideSetupBranch()`
  - 输入：`detectSetupEnvironment()` 结果 + 用户选择（如是否覆盖）
  - 输出：`{ kind: 'reuse_current' | 'repair_current' | 'unparseable_current' | 'migrate_legacy' | 'fresh_init' | 'cancelled' }`
  - 不做任何 I/O

- `mapConfigErrorsToRepairFields()`
  - 输入：结构化配置错误列表
  - 输出：`{ mode: 'repair' | 'manualReview', fields: string[] }`
  - 只做“错误 -> 提问字段”映射

- `persistSetupConfig()`
  - 输入：最终 config draft + `hasExistingConfig` + 当前配置文件扩展名
  - 输出：`{ configChanged: boolean, configPath: string, backupPath?: string }`
  - 负责 validate + backup + write；备份失败时抛错

- `ensureSetupServiceReady()`
  - 输入：`{ configChanged, detectedService, desiredPort, reloadSupported }`
  - 其中 `detectedService.kind` 必须是 `self_healthy | self_unhealthy | none | non_self_occupied`
  - 输出：成功时返回 `{ action: 'reuse' | 'start' | 'reload' | 'restart', healthChecked: true }`；失败时抛出明确错误
  - 负责服务矩阵判断与最终健康检查

- `runSetup()`
  - 只允许调用上述 seam，不得自行拼接备份命名、服务复用矩阵或 repair 映射规则

## Operational Decisions

- 备份文件命名使用 UTC 时间戳 `YYYYMMDDTHHmmssSSS`，格式为 `config.setup.<timestamp>.bak.<ext>`。
- 保留原扩展名：`yaml` / `yml` / `json`。
- 若同毫秒发生冲突，在文件名末尾追加短随机后缀。
- 备份文件写在现有配置目录下。
- 备份失败时停止 setup，不继续覆盖写入。
- `reloadSupported` 由 service 层依赖显式注入，不在 orchestrator 中猜测。
- 进入 `ctr code` 继续复用现有 `runClaudeCode()` 进程模型与退出码传递方式，不新造一套 spawn / exit 逻辑。

## Service Matrix

| 条件 | 动作 |
|---|---|
| `configChanged=false` + `detectedService.kind=self_healthy` | `reuse` |
| `configChanged=false` + `detectedService.kind=none` | `start` |
| `configChanged=false` + `detectedService.kind=self_unhealthy` | `restart` |
| `configChanged=true` + `detectedService.kind=none` | `start` |
| `configChanged=true` + `detectedService.kind=self_healthy` + `reloadSupported=true` | `reload` + 最终健康检查 |
| `configChanged=true` + `detectedService.kind=self_healthy` + `reloadSupported=false` | `restart` + 最终健康检查 |
| `configChanged=true` + `detectedService.kind=self_unhealthy` | `restart` + 最终健康检查 |
| `detectedService.kind=non_self_occupied` | `fail` |
