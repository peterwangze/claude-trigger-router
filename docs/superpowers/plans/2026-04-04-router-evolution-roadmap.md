# Claude Trigger Router 演进计划

> 基于 `advice/演进思路.md`，结合当前仓库已具备的 `TriggerRouter`、`SmartRouter`、`ctr setup`、配置校验与健康检查能力，整理出的下一阶段产品/架构演进路线图。

## 1. 现状判断

当前项目已经完成了第一层“可用型路由器”能力：

- 已有 `Router.default / think / longContext / webSearch / background` 等基础分流能力
- 已有 `TriggerRouter`，可以通过规则做高确定性路由
- 已有 `SmartRouter`，可以在候选模型中做一次 LLM 决策
- 已有 `ctr setup` 方向的首次使用文档与实现骨架，产品化入口开始成型
- 已有配置校验、服务探活、CLI 主路径，具备进一步工程化演进的基础

但如果目标是把项目从“多模型转发器”推进到“模型治理层”，当前还缺 4 类关键能力：

1. 缺少跨模型切换时的上下文连续性治理
2. 缺少失败后自动升级的级联推理门控
3. 缺少比关键词更稳健的语义意图识别
4. 缺少对低质量输出的异步校验与拦截机制

这意味着项目已经具备“路由”雏形，但还没有真正具备“治理”能力。

## 2. 演进目标

下一阶段的目标不是继续堆更多静态规则，而是把 Claude Trigger Router 演进为一个面向 Claude Code 的本地模型治理层：

- 对话内保持路由稳定，不轻易因为单轮关键词抖动而频繁换模型
- 当模型输出质量不足时，能够自动升级推理强度而不是把失败暴露给用户
- 在规则不足时，能用低成本语义能力补足意图识别
- 对高风险模型输出增加“信任但验证”的监工链路
- 让成本、稳定性、时延、质量这四个维度可以被配置、观测、追踪

一句话总结：

> 从“把请求发给另一个模型”，演进为“在本地对模型选择、升级、验证和连续性进行治理”。

## 3. 演进原则

### 3.1 渐进增强

每一阶段都必须能够单独落地、单独回滚，避免一次性引入过多隐式行为。

### 3.2 默认保守

所有高级治理能力都应支持显式开关，默认不破坏现有用户路径。

### 3.3 先观测后自动化

在自动升级、自动拦截之前，先把命中原因、耗时、成本和失败证据记录清楚。

### 3.4 低成本优先

高级治理能力应优先采用“廉价模型判断 + 强模型兜底”的结构，而不是默认全程最贵模型。

### 3.5 失败可降级

任一治理组件失败时，系统仍应能够回退到当前稳定的 `TriggerRouter/SmartRouter/Router.default` 路径。

## 4. 北极星能力图

目标架构可抽象为 5 层：

1. **输入归一化层**：提取请求文本、工具信息、token 规模、会话标识
2. **决策治理层**：Sticky Routing、Semantic Intent、SmartRouter、Cascade Gate
3. **执行协调层**：模型切换时的 Context Alignment、失败重试、升级重投
4. **质量监督层**：Shadow Supervisor、输出质量规则、异步校验
5. **可观测层**：路由原因、成本、时延、失败码、升级记录、验证结果

## 5. 四条主线能力

### 主线 A：状态感知的粘性路由

目标：

- 让同一任务在多轮对话中尽量保持模型一致
- 必须切换模型时，自动补一段技术上下文摘要，降低交接损失

直接收益：

- 降低跨模型切换导致的代码风格漂移
- 降低模型无法理解前序隐含决策的问题

### 主线 B：级联推理门控

目标：

- 默认先走标准成本路径
- 当出现编译失败、占位符、空洞回答、静态检查失败时，再自动升级

直接收益：

- 控制高阶 reasoning 成本
- 把“失败后重投”变成系统能力而不是人工操作

### 主线 C：语义增强路由

目标：

- 在关键词规则之外增加语义层判断
- 用意图向量/嵌入相似度补足表达差异

直接收益：

- 用户不必精确命中规则关键词
- 减少规则爆炸和维护负担

### 主线 D：影子监工模式

目标：

- 对特定模型、特定任务、特定风险等级的输出做异步审查
- 命中偷懒/占位符/明显缺失时触发拦截、降级或重试

直接收益：

- 提升输出下限
- 为后续自动治理提供数据闭环

## 6. 推荐分期

## 阶段 0：治理基础设施补齐

时间建议：1-2 周

范围：

- 统一路由决策日志结构
- 引入 request/session 级 trace id
- 增加路由原因、升级原因、验证结果、失败类型的可观测字段
- 为后续 Sticky/Cascade/Semantic/Shadow 预留配置结构

验收标准：

- 能在日志中看出每次命中是规则、智能、语义还是升级触发
- 能追踪一次请求是否发生模型切换、是否发生升级、是否进入验证

## 阶段 1：State-Aware Sticky Routing

时间建议：2-3 周

范围：

- 建立 session state store
- 为会话绑定最近成功模型、任务类型、摘要缓存
- 在模型切换时自动触发 Context Alignment 摘要注入

验收标准：

- 同一会话连续请求优先复用最近稳定模型
- 发生跨模型切换时，系统可自动生成并注入技术摘要
- Sticky 命中和切换原因可观测

## 阶段 2：Cascaded Reasoning Gate

时间建议：2-3 周

范围：

- 定义升级触发器：编译失败、测试失败、出现 `TODO`、省略输出、结构化校验失败
- 建立标准档 -> 高推理档 -> 抢救档的升级链
- 支持把失败日志与关键信息回注给升级模型

验收标准：

- 常规请求仍走标准模型
- 命中失败证据时自动升级，不需要人工二次提问
- 升级前后成本、时延、成功率可观测

## 阶段 3：Semantic-Augmented Trigger

时间建议：3-4 周

范围：

- 定义核心意图集合：架构变更、复杂推理、Bug 修复、文档、配置、审查等
- 接入本地 embedding/语义分类能力
- 构建“规则优先 + 语义补足 + SmartRouter 兜底”的混合决策链

验收标准：

- 对非关键词表达仍能稳定命中正确意图
- 语义层误命中率可被追踪和调优
- 语义能力关闭时，系统行为退化回现有逻辑

## 阶段 4：Shadow Supervisor

时间建议：3-4 周

范围：

- 对指定模型或指定任务开启影子审查
- 支持同步阻断与异步告警两种模式
- 引入最小质量规则：长度异常、`TODO`、占位符、未完成代码块、结构化字段缺失

验收标准：

- 能识别并记录低质量输出
- 高风险场景支持自动重试或升级
- 审查链路可配置采样率，避免成本失控

## 阶段 5：运营化与策略产品化

时间建议：2 周

范围：

- 汇总治理指标
- 输出可维护的治理配置模板
- 完成文档与默认策略示例

验收标准：

- 用户可以理解何时启用哪类治理能力
- 配置模板可直接复制启用
- 至少有一套“低成本优先”和一套“高质量优先”的策略预设

## 7. 优先级建议

建议优先顺序：

1. 先做阶段 0，可观测性和配置骨架
2. 再做阶段 1，保证跨模型连续性
3. 接着做阶段 2，把失败升级闭环打通
4. 然后做阶段 3，增强路由识别能力
5. 最后做阶段 4，把质量监管闭环接上

原因：

- Sticky Routing 和 Cascade Gate 都依赖稳定的 session、trace 和失败证据
- Semantic Router 的价值在于提效和提准，但前提是治理链可观测
- Shadow Supervisor 成本更高，应在前面三项稳定后再推进

## 8. 对当前仓库的落地映射

建议新建一层治理域模块，而不是继续把所有逻辑堆进 `src/trigger/`：

- `src/governance/`
  - `types.ts`
  - `session-store.ts`
  - `context-alignment.ts`
  - `cascade-gate.ts`
  - `semantic-router.ts`
  - `shadow-supervisor.ts`
  - `metrics.ts`
  - `policy.ts`

现有模块的承接关系建议如下：

- `src/trigger/`：继续负责规则、意图、SmartRouter 等“路由入口层”
- `src/router/`：继续负责最终模型决策落地
- `src/governance/`：新增负责“跨轮状态、升级、验证、治理策略”
- `src/utils/config.ts`：新增治理配置默认值与校验
- `src/server.ts`：承接治理日志、指标暴露和中间件接线

## 9. 成功指标

至少追踪以下指标：

- 路由命中分布：规则 / 语义 / SmartRouter / Sticky / Cascade Upgrade
- 跨模型切换率
- 升级触发率与升级成功率
- 影子审查命中率
- 用户可见失败率
- 平均请求成本与 P95 延迟
- 高质量任务命中强模型的准确率

目标不是让所有指标都变小，而是让质量、成本、时延三者变得可权衡、可解释。

## 10. 风险与约束

### 技术风险

- 本地会话识别不稳定，可能导致 Sticky 命中错误
- 上下文摘要质量不高时，反而可能放大错误
- 语义路由模型或 embedding 模型引入新的部署复杂度
- 影子监工如果设计成同步阻断，可能明显增加延迟

### 产品风险

- 自动升级如果不可解释，会让用户觉得“为什么换模型了”
- 规则、语义、智能、升级多层叠加后，配置复杂度会上升

### 控制策略

- 所有高级能力支持独立开关和可观测日志
- 先以告警/记录模式上线，再逐步切换到自动执行
- 用配置模板收敛复杂度，而不是强迫用户自己拼装所有策略

## 11.1 2026-04-06 进度校准

结合 2026-04-04 到 2026-04-06 的实际提交与代码现状，路线图需要补充如下状态说明：

- 阶段 0 到阶段 4 的核心治理能力已经完成首轮落地，不再处于规划态
- 当前主线已经从“治理能力补齐”进入“指标观测增强 + 配置产品化”阶段
- `/ui` 已从调试页演进为配置工作台，承担了 models 草稿编辑、引用影响分析、修复建议、preset 预览与 dry-run 等能力
- `ctr setup` 已不再只是首次使用向导骨架，而是与 `Models` 抽象、provider template、迁移路径一起形成配置主入口的一部分

因此，当前阶段的实际推进顺序应更新为：

1. 治理底座与主链能力已完成并进入稳定化
2. 指标观测与导出归档能力持续增强
3. 配置易用性进入第二主线，包括 `Models` 抽象、setup 简化和 `/ui` 草稿工作台
4. 后续再回到“统一 provider 接口抽象、消息格式转换、最简模型配置参数”这一轮产品化收口

这不构成架构偏航，但意味着项目已经从“按治理阶段推进”扩展为“双主线推进”：

- 主线一：治理能力与观测运营
- 主线二：配置与使用易用性产品化

## 12. 结论

这次演进不建议再把重点放在“继续增加几条路由规则”，而应把项目正式推向：

- 有状态
- 可升级
- 可验证
- 可观测
- 可运营

这 5 个关键词，才是 Claude Trigger Router 从“路由器”走向“模型治理层”的分水岭。
